# ADR-001: Static GitHub Pages Architecture

## Status
Accepted

## Context
The Eskdale Art Show website needs rebuilding from a ~2005-era page. The site is maintained by a small community group with varying technical ability. It must be cheap to host, easy to update, and reliable.

## Decision
Build as a static HTML/CSS/JS site deployed to GitHub Pages via GitHub Actions.

**No static site generator** (Hugo, Jekyll, Astro, etc.) — the site is a single page with a few JSON data files. An SSG adds build complexity, framework lock-in, and a learning curve for contributors, with no proportionate benefit.

## Consequences
- **Positive**: Zero hosting cost, no server to maintain, version-controlled content, PR-based review workflow, instant rollback via git revert
- **Positive**: Contributors edit plain HTML/CSS/JSON — no framework knowledge required
- **Negative**: No templating — repeated HTML must be managed manually (mitigated by JS rendering from JSON data)
- **Negative**: No build-time image optimisation (mitigated by manual WebP conversion and lazy loading)

# ADR-002: WASM Brushstroke Effect as Discrete Module

## Status
Accepted

## Context
The site should have visual flair befitting an art show, but the WASM module must not create maintenance burden for community contributors.

## Decision
Implement the brushstroke particle effect as an isolated Rust/WASM crate in `wasm/`, built by GitHub Actions, with output committed to `src/wasm/pkg/`. The effect is loaded as a progressive enhancement — the page is fully functional without it.

### Architecture
- `wasm/` contains Cargo.toml and Rust source — only touched by developers
- `src/wasm/pkg/` contains the built `.wasm` and JS glue — generated by CI
- `src/js/main.js` dynamically imports the WASM module with feature detection
- Canvas overlay uses `pointer-events: none` and `aria-hidden="true"`

## Consequences
- **Positive**: Contributors never need Rust toolchain — CI builds it
- **Positive**: Effect degrades gracefully on unsupported browsers and reduced-motion preferences
- **Positive**: ~15KB over the wire (brotli), negligible performance impact
- **Negative**: CI pipeline needs wasm-pack installed (one-time workflow setup)
- **Negative**: Debugging requires Rust knowledge (but the module is <300 lines)

# ADR-003: Pages CMS for Community Content Management

## Status
Accepted

## Context
Non-technical art show committee members need to update event details, add gallery images, and edit text without using git or a code editor.

## Decision
Integrate Pages CMS (pagescms.org) — a free, open-source, GitHub-native CMS that provides a web UI for editing structured JSON files in the repository.

### How It Works
1. Content stored as JSON files in `src/data/` (event.json, gallery.json, about.json)
2. `.pages.yml` at repo root defines the editing schema
3. Contributors visit pagescms.org, authenticate with GitHub, select the repo
4. CMS presents structured forms matching the JSON schema
5. Edits commit directly to the repo via GitHub API
6. GitHub Actions deploys the updated site

### Why Not Decap/Sveltia CMS
Both require an OAuth proxy for GitHub Pages (Netlify provides one only for Netlify-hosted sites). Pages CMS handles auth natively with zero infrastructure.

## Consequences
- **Positive**: Zero infrastructure — no OAuth proxy, no backend, no database
- **Positive**: Simple setup — one `.pages.yml` config file
- **Positive**: Contributors see form fields, not code
- **Positive**: Image uploads supported
- **Negative**: Contributors need GitHub accounts
- **Negative**: Dependency on pagescms.org hosted service (mitigable: can self-host on Cloudflare Workers)
- **Negative**: Newer project with smaller community than Decap CMS
